# 📄 求职材料 - 企业智能知识库Agent

## 📝 简历项目描述

### 项目名称
**企业智能知识库Agent** - 基于 RAG 混合检索 + 多用户隔离的企业知识库问答系统

### 项目时间
2026年6月

### 项目描述
独立开发的企业级知识库问答系统，基于 LangGraph 状态图工作流编排意图路由，结合 RAG（检索增强生成）混合检索引擎。采用向量检索 + BM25 关键词检索 + RRF 融合排序的混合检索策略，支持 HyDE 查询改写。系统支持多用户认证、个人/共享双空间隔离、流式对话和参考来源预览，有效提升企业知识管理效率。

### 技术栈
- **后端**：FastAPI + Python 3.10+
- **前端**：Streamlit
- **工作流**：LangGraph（状态图编排意图路由）
- **AI 框架**：LangChain + langchain_openai
- **大模型**：MIMO-v2.5（小米大模型）
- **向量数据库**：ChromaDB（支持元数据过滤）
- **检索引擎**：向量检索 + BM25 检索 + RRF 融合排序 + HyDE 查询改写
- **Embedding**：fastembed (BAAI/bge-small-en-v1.5)
- **认证**：bcrypt + PyJWT
- **部署**：Docker + Docker Compose

### 核心职责与成果

1. **RAG 混合检索引擎设计与实现**
   - 设计向量检索（语义相似性）+ BM25 关键词检索的混合策略
   - 实现 Reciprocal Rank Fusion (RRF) 融合排序，两路结果按排名融合
   - 实现 BM25 元数据过滤，支持按 owner/visibility 精确过滤，确保多用户数据隔离
   - 预留 CrossEncoder 重排序接口（BAAI/bge-reranker-base）

2. **多用户认证与空间隔离**
   - 实现 JWT 认证流程：bcrypt 密码哈希 + PyJWT Token + 24小时有效期
   - 设计个人工作区（private）和团队共享库（public）双空间
   - 文档替换机制：原上传者可覆盖更新同名文档（delete + re-add 原子操作）
   - 实现 Agent 实例池：TTL 自动回收（1小时）+ 容量上限（50）+ 线程锁

3. **流式对话架构**
   - 后端 SSE（Server-Sent Events）流式推送 LLM 回答
   - 前端后台线程 + Queue 异步接收，阻塞 get(timeout=1.0) 避免 CPU 空转
   - 流式期间禁用来源预览按钮，防止 UI 冲突；120 秒超时保护

4. **智能记忆与上下文管理**
   - 滑动窗口：消息超阈值时旧消息自动压缩为 LLM 摘要
   - 知识库感知：空知识库时自动过滤历史中的知识库问答，防止 LLM 从历史中"回忆"已删除内容
   - 用户偏好和对话摘要自动注入 system prompt

### 技术亮点

1. **混合检索 + RRF 融合**
   - 向量检索基于 fastembed 生成语义向量，捕捉深层语义关系
   - BM25 基于 jieba 中文分词，对专有名词、精确匹配效果好
   - RRF 融合公式 `score = Σ 1/(k + rank_i)`，在两路检索中都排名靠前的文档融合分数更高
   - BM25 支持元数据过滤，私有文档不会泄露到共享搜索结果

2. **先检索后生成架构**
   - 用户提问 → RAG 混合检索 → 构建上下文 → LLM 生成回答
   - 系统提示词区分「有检索结果」和「无检索结果」两种场景
   - 来源标注格式：`📚 来源：《文件名.pdf——片段x》`

3. **多用户 Agent 实例池**
   - 每个用户独立 Agent 实例，避免状态交叉
   - TTL 自动回收闲置实例，防止内存泄漏
   - 容量上限 + LRU 驱逐，控制资源消耗
   - threading.Lock 保证线程安全

4. **工程化实践**
   - FastAPI RESTful API + Swagger 自动文档
   - JWT 认证中间件（兼容 Swagger UI Authorize）
   - Docker 多容器编排 + 健康检查
   - 单元测试覆盖核心模块
   - 独立流式线程池（max_workers=10）避免占用 FastAPI 默认线程池
   - BM25 异步重建去重（`_bm25_rebuilding` 标志防止线程膨胀）
   - Tavily 搜索 15 秒超时保护
   - 对话压缩后截断历史，避免重复压缩
   - 客户端断开检测（stop_event 跨线程通知 + asyncio 超时检测）

### 项目难点与解决方案（1分钟）

#### 难点 1：BM25 数据隔离

**问题**：BM25 检索不支持元数据过滤，私有文档会泄露到共享搜索结果

**解决方案**：
- 在 BM25 检索结果返回后，按 owner/visibility 元数据进行后过滤
- 实现 `_match_bm25_metadata` 方法，支持简单键值对和 `$and` 组合条件
- 在 `hybrid_search` 中同时将 `where` 参数传递给向量检索和 BM25 检索

**成果**：私有文档不会出现在共享搜索结果中，多用户数据完全隔离

#### 难点 2：删除知识库后 LLM 仍引用旧内容

**问题**：删除知识库文档后，LLM 仍可能从对话历史中回答知识库相关的内容

**解决方案**：
- 系统提示词区分「有检索结果」和「无检索结果」两种场景
- 空知识库时自动过滤历史中的知识库问答（通过检测 `📚 来源` 标记）
- 删除文档时同步清空对话摘要，防止从摘要中"回忆"

**成果**：删除知识库后 LLM 不再引用已删除的内容

#### 难点 3：流式输出期间的 UI 冲突

**问题**：流式输出期间点击参考来源按钮会触发 Streamlit rerun，中断流式响应

**解决方案**：
- 流式期间通过 `_is_chatting` 状态禁用所有来源预览按钮
- 使用 `@st.fragment` 独立渲染侧边栏，聊天流式输出时仍可操作侧边栏
- 前端使用阻塞 `get(timeout=1.0)` 替代 `get(timeout=0.05)` 避免 CPU 空转

**成果**：流式输出稳定，不被 UI 操作中断

## 🎯 面试问答准备

### Q1: 为什么选择 LangGraph 而不是简单的 if-else 路由？

**回答**：
"LangGraph 的状态图可以清晰表达多路由逻辑，支持条件分支和循环。我的系统有四种路由（general/internal/external/external_disabled），internal 路由还有 internal_first 的降级逻辑（内部无结果自动转外部）。用 LangGraph 的 conditional edges 可以把这些逻辑声明式地表达出来，比 if-else 嵌套更清晰、更易维护。而且 LangGraph 的状态是 TypedDict，可以透传上下文数据（sources、chunks 等），比手动传参更规范。"

### Q2: 多用户隔离是怎么实现的？

**回答**：
"三层隔离：第一层是 JWT 认证，每个请求通过 Token 提取 user_id；第二层是向量库元数据过滤，ChromaDB 的 where 子句按 owner 和 visibility 过滤；第三层是 BM25 后过滤，检索结果返回后按元数据精确匹配。文档删除也按 filename + owner + visibility 三重条件，防止误删同名不同空间的文档。"

### Q3: Agent 实例池为什么需要 TTL 回收？

**回答**：
"每个用户有独立的 Agent 实例，包含对话历史、RAG 引擎等状态。如果用户长期不操作，实例会一直占用内存。我设计了 TTL 自动回收机制：每次访问刷新时间戳，超过 1 小时未访问的实例自动清理。同时有容量上限 50 个实例，超出时驱逐最久未访问的。threading.Lock 保证并发安全。"

### Q4: 删除知识库后 LLM 为什么还会引用旧内容？

**回答**：
"这是对话历史导致的。LLM 的上下文包含历史对话，其中有之前基于知识库的问答。我做了三重防护：第一，系统提示词明确区分有检索结果和无检索结果两种场景；第二，空知识库时自动过滤历史中的知识库问答（通过检测来源标记）；第三，删除文档时同步清空对话摘要。"

### Q5: 流式输出期间为什么不能点击参考来源？

**回答**：
"Streamlit 的交互模型是每次操作触发整个脚本重新执行。如果流式输出期间用户点击来源按钮，会触发 rerun，中断流式响应。我的解决方案是在流式期间通过 _is_chatting 状态禁用所有来源按钮。同时用 @st.fragment 独立渲染侧边栏，这样聊天流式输出时用户仍可以操作侧边栏上传文档等。"

### Q6: 流式对话中客户端断开怎么处理？

**回答**：
"流式对话涉及两个线程：前端 SSE 的异步生成器（generate）和后台的 LLM 生成线程（_run_sync）。客户端断开时，我用三重检测：第一，asyncio.wait_for 超时 1 秒检测队列空闲；第二，request.is_disconnected() 检查 HTTP 连接状态；第三，asyncio.CancelledError 捕获协程取消。检测到断开后，通过 stop_event（threading.Event）跨线程通知后台线程停止 LLM 生成。中断时不保存记忆，避免保存不完整的回答。流式请求使用独立的 ThreadPoolExecutor(max_workers=10)，不占用 FastAPI 默认线程池。"

### Q7: HyDE 查询改写是什么？为什么需要它？

**回答**：
"HyDE（Hypothetical Document Embeddings）的思想是：用户的短查询（比如'请假制度'）和知识库中的文档在向量空间中可能距离较远。HyDE 先让 LLM 根据查询生成一段假设性的文档内容（比如'公司员工请假制度规定...'），再用这段假设性文档去检索，因为假设性文档的表述更接近真实文档，检索召回率会更高。我只对短查询（<8字符）或包含模糊指代的查询启用 HyDE，避免对长查询增加不必要的延迟。"

### Q8: 文档去重是怎么实现的？如何处理同名文件？

**回答**：
"我设计了两阶段去重策略。第一阶段是 MD5 哈希精确匹配：上传文件时计算内容哈希，如果知识库中已有同名且同哈希的文档，直接跳过（内容完全相同无需重复上传）。第二阶段是文件名匹配：如果同名但哈希不同（内容有更新），提示用户是否替换。替换时会检查当前用户是否为文档所有者（is_document_owner），只有原上传者才能替换，防止他人覆盖。私有文档按 owner + visibility 隔离，公共文档全局去重。"
