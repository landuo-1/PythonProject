# 企业智能知识库Agent - 项目描述

## 一句话描述
基于 LangGraph 工作流 + RAG 混合检索 + 多用户隔离的企业知识库问答系统

## 技术栈
`Python` `FastAPI` `LangGraph` `LangChain` `RAG` `ChromaDB` `BM25` `RRF` `HyDE` `JWT` `Streamlit` `Docker` `SSE` `asyncio`

---

## 简历项目描述（200字）

独立开发的企业级知识库问答系统，基于 LangGraph 状态图工作流编排意图路由，结合 RAG 混合检索引擎实现多用户隔离的智能问答。搭建向量检索 + BM25 关键词检索双路召回架构，采用 RRF 倒数排名融合排序，实测 Recall@5 达 95%，比纯向量检索高 15 个百分点（80%→95%），MRR 提升 21%（0.652→0.789）。针对 ChromaDB 原生 BM25 不支持元数据过滤的框架限制，独立实现后过滤层，确保私有文档不跨用户泄露。设计 Agent 实例池（TTL 回收 + LRU 驱逐 + 线程锁）实现实例复用，SSE 流式对话通过 stop_event 跨线程信号量解决客户端断开后的 LLM 生成中断问题，知识库感知的历史过滤 + 滑动窗口摘要压缩机制从检索层治理幻觉。

## 面试口述版

### 开场（30秒）

> "我做了一个企业智能知识库Agent，核心是 LangGraph 工作流 + RAG 混合检索。用户提问后，意图路由器自动分类为闲聊、内部知识库检索、外部网络搜索三种路径。内部问题走 RAG 混合检索，我搭建了向量 + BM25 双路召回 + RRF 融合的架构，实测 Recall@5 达到 95%，比纯向量高 15 个百分点。系统支持多用户认证，个人工作区和团队共享库双空间隔离。"

### 技术亮点讲解

#### 1. 混合检索引擎（核心亮点）

> "我搭建了向量检索 + BM25 关键词检索的双路召回架构。向量检索基于 fastembed 生成语义向量，捕捉深层语义关系；BM25 基于 jieba 中文分词，对专有名词和精确匹配效果好。两路结果用 RRF（倒数排名融合）合并，公式是 score = Σ 1/(k+rank)，比加权平均对分数尺度差异更鲁棒。
>
> 我在 15 篇企业文档（49 个片段）上做了基准测试，20 条查询覆盖人事、财务、产品、技术等领域。结果是：纯向量 Recall@5 是 80%，混合检索达到 95%，提升了 15 个百分点。MRR 从 0.652 提升到 0.789，提升了 21%。这说明混合检索不仅找得到，还能把正确结果排得更靠前。
>
> 另外 ChromaDB 原生不支持 BM25 的元数据过滤，我独立实现了后过滤层，按 owner 和 visibility 精确匹配，确保私有文档不泄露到共享搜索结果。"

**演示**：上传文档 → 提问 → 展示检索结果和来源标注

#### 2. 意图路由

> "意图路由基于 LangGraph StateGraph，支持 5 种路由：general（闲聊）、internal（知识库）、external（网络搜索）、external_disabled（搜索未开提示）、internal_first（优先内部无结果转外部）。路由策略分三级：关键词快速匹配 → LLM 语义分类 → 规则降级。LLM 分类器不依赖搜索开关状态，对模糊问题先探明语义方向，避免外部问题误走内部检索导致答非所问。"

**演示**：展示不同问题类型的路由效果

#### 3. 流式对话与客户端断开处理

> "对话采用 SSE 流式推送，通过 asyncio.Queue 桥接同步生成器与异步响应。客户端断开时用三重检测：asyncio.wait_for 超时、request.is_disconnected()、asyncio.CancelledError。检测到断开后，通过 stop_event（threading.Event）跨线程通知后台停止 LLM 生成，中断时不保存不完整回答。流式请求使用独立的 ThreadPoolExecutor(max_workers=10)，不占用 FastAPI 默认线程池。"

#### 4. 幻觉治理

> "用户删除知识库文件后，LLM 可能从对话历史中引用已删内容。我设计了两层防护：第一，知识库为空时自动过滤历史中的知识库问答（通过检测来源标记）；第二，滑动窗口摘要压缩，压缩后截断历史避免重复压缩，用 _compress_lock 双重检查锁防止并发压缩。"

#### 5. 文档去重与替换

> "文档上传采用两阶段去重：第一阶段 MD5 哈希精确匹配，内容完全相同直接跳过；第二阶段文件名匹配，同名不同内容提示替换。替换时通过 is_document_owner 检查权限，只有原上传者才能覆盖。"

### 检索性能实测数据

| 指标 | 纯向量检索 | 混合检索（向量+BM25+RRF） | 提升 |
|------|-----------|--------------------------|------|
| **Recall@5** | 80.0% | **95.0%** | **+15pp** |
| **MRR** | 0.652 | **0.789** | **+21.0%** |
| 检索延迟 | **7ms** | 304ms | 向量极快 |
| 初始化耗时 | 0.83s | - | 含 embedding 模型加载 |

**测试条件**：15 篇企业文档 / 49 个片段 / 20 条查询 / chunk_size=500 / BAAI/bge-small-en-v1.5

**核心结论**：
- 混合检索 Recall@5 达 95%，比纯向量高 15 个百分点
- MRR 从 0.652 提升到 0.789（+21%），正确结果排名显著靠前
- BM25 对专有名词（KPI、SLA、MySQL 等）的精确匹配弥补了向量检索的语义盲区

## 面试问答准备

### Q1: 为什么选 RRF 而不是加权平均？

> "RRF 用排名的倒数融合，不依赖原始分数。向量检索和 BM25 的分数范围完全不同——向量是 0-1 的余弦相似度，BM25 是无界的 TF-IDF 分数。加权平均需要先归一化，而 RRF 直接按排名融合，对分数尺度差异天然鲁棒。实测也验证了效果，MRR 提升了 21%。"

### Q2: BM25 不支持元数据过滤怎么解决？

> "ChromaDB 的 BM25 是独立的稀疏检索，不走 ChromaDB 的 where 子句。我在 BM25 检索结果返回后，实现 _match_bm25_metadata 方法做后过滤，支持简单键值对和 $and 组合条件。在 hybrid_search 中同时将 where 参数传递给向量检索和 BM25 检索，确保两边结果都经过过滤。"

### Q3: Agent 实例池为什么需要 TTL 回收？

> "每个用户有独立的 Agent 实例，包含对话历史、RAG 引擎等状态。如果用户长期不操作，实例会一直占用内存。TTL 自动回收机制：每次访问刷新时间戳，超过 1 小时未访问的实例自动清理，同时持久化长期记忆。容量上限 50 个实例，超出时驱逐最久未访问的。"

### Q4: 流式对话中客户端断开怎么处理？

> "流式对话涉及两个线程：前端 SSE 的异步生成器和后台的 LLM 生成线程。客户端断开时用三重检测，检测到后通过 stop_event 跨线程通知后台停止生成。中断时不保存记忆，避免保存不完整的回答。"

### Q5: HyDE 是什么？什么时候用？

> "HyDE 的思想是：用户的短查询和知识库文档在向量空间中距离较远。HyDE 先让 LLM 生成一段假设性文档，再用假设性文档去检索，因为表述更接近真实文档，召回率更高。我只对短查询（<8 字符）或包含模糊指代的查询启用，避免对长查询增加不必要的延迟。"

### Q6: 混合检索的延迟开销能接受吗？

> "混合检索延迟 304ms，比纯向量的 7ms 慢，主要开销在 jieba 分词和 BM25 计算。但 300ms 对用户来说是可接受的（人眼感知阈值约 500ms）。而且 Recall 从 80% 提升到 95%，这个 trade-off 是值得的。如果要进一步优化延迟，可以考虑缓存 BM25 索引、使用更轻量的分词器，或者只在向量检索结果不足时才启用 BM25。"
